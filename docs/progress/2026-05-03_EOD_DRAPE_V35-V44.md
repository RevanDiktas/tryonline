## What broke and what shipped, in order

### `ff6d11c` v35: frontend MTL rewrite to blob URLs before parse

Three.js r160 MTLLoader.parse() returns a MaterialCreator where
materials.materials stays empty until preload(). The old code iterated
materials.materials BEFORE preload() then called preload() with empty
baseUrl, so every map_Kd 404'd silently. Fix: regex-rewrite the MTL text
inline with blob: URLs before parse, so MTLLoader resolves textures
naturally.

This was textures fix attempt 1. It didn't end up being the actual texture
bug, but the fix is good and stays.

### `f47b928` v36: skip Newton sim entirely, ship retarget result

THE structural breakthrough. v18-v35 ran Newton XPBD on top of the v26
retarget. cloth_reference_drag was a warmup force designed for FLAT 2D
PATTERNS being guided to 3D body regions. Our pipeline starts with a
CLO3D-DRAPED 3D garment that's already correctly positioned, so drag has
no useful work but did all the visible damage we'd been chasing for a
week (hood yanked to shoulder, sleeves crossed, pants flying). v36 stops
the sim and ships the retargeted mesh directly.

Body collisions immediately dropped to 0. Drape time dropped from ~96s
to ~15-20s. v36 is the structural answer the previous week of tweaking
was avoiding.

### `38e005f` v37: retarget offset 12mm + frontend sRGB colorSpace

Front view in v36 still showed bow-tie skin patches at the chest, waist,
and front thighs because (1) drape-test.html renders avatar_textured.glb
but the handler retargets against body_apose.obj (different topology at
convex apex regions, so 5mm offset wasn't enough buffer), and (2) face-
plane interpolation between verts at 5mm sdf can dip below the body. Bump
target_offset 5mm to 12mm and n_iters 15 to 25.

Frontend: set mat.map.colorSpace = SRGBColorSpace because three.js r160
defaults textures to NoColorSpace which renders washed-out.

After v37, every drape test had clean drape and zero pokethrough.

### `b687438` v38: build materials manually, bypass MTLLoader.preload

Even with v35's blob-URL rewrite, the orange RAMIN prints rendered
invisible. Bypass MTLLoader's preload() lifecycle entirely. Use
MTLLoader.parse() only to extract the materialsInfo dict, then construct
THREE.MeshStandardMaterial per material name ourselves with explicit
TextureLoader + SRGBColorSpace. Override materials.materials,
materials.create, materials.preload so OBJLoader uses our handcrafted
materials.

Texture diagnostics now logged at the test page (materials parsed, blob
URLs available, materials with diffuse map, missing-map names). Future
texture failures will be loud.

### `ee1605d` v39: fix mtllib name mismatch killing texture packaging

Real bug found. CLO3D's OBJ has `mtllib mm.mtl` (two m's), Supabase only
hosts `m.mtl` (one m). Input-side download flow correctly falls back to
m.mtl. Output-side packager reads mtllib from the draped OBJ, gets
"mm.mtl", looks for it on disk, fails, and silently skips the entire
MTL+textures packaging block. Response went out with empty
draped_mtl_base64 and empty draped_textures_base64 the entire time.
v35-v38 frontend efforts couldn't possibly work because the backend was
shipping nothing.

Two-layer fix: (1) input-side aliases the downloaded MTL under the OBJ's
expected name, (2) output-side scans garment_obj.parent for any `.mtl`
if mtllib doesn't resolve.

### `8ea6a5e` v40: alpha-test transparency on print decal materials

After v39, prints loaded but rendered with a white rectangle background
around the orange. The PNGs are RGBA with 73% transparent (alpha=0) where
RGB is pure white. Without alpha-aware rendering, three.js renders alpha=0
as opaque white. Fix: `mat.transparent=true, mat.alphaTest=0.5` on
materials with map textures. Crisp binary cutout, underlying body fabric
shows through transparent regions.

### `ebfca41` v41: MeshBasicMaterial for decals + toneMapped off

After v40, prints showed crisp edges but the orange was desaturated to
tan/beige. The texture's actual color is `#fcb040` (vivid orange) but
ACESFilmicToneMapping + MeshStandardMaterial PBR was attenuating to ~60%
saturation. Decals shouldn't be PBR-shaded anyway, they're flat printed
graphics. Switch decal materials to MeshBasicMaterial with
toneMapped=false. Cloth fabric stays MeshStandardMaterial for 3D shading.

Result: vivid orange textures, fabric still has 3D depth.

### `be050a2` v42: polygon offset for decals + body-color override

After v41, prints were vivid but a black geometric blob with ragged edges
was covering most of the print area. Z-fighting between print panels and
body fabric (both at body+12mm after retarget). Plus FABRIC_2 (Kd=0.82
light gray, the zipper binding) was rendering as a "white background"
behind the prints.

Two structural fixes: (1) `polygonOffset` on print materials pulls them
toward camera in the depth buffer, winning z-fights, (2) override
non-Body non-textured Kd to dominant body color so FABRIC_2 stops
rendering gray.

### `b701137` v43: restore zipper via depth layering, drop Kd override

v42's color override worked for hiding the print backing component of
FABRIC_2 but also killed the visible zipper component (CLO3D draws the
zipper as gray). The user wanted both: print backing hidden AND zipper
visible.

Right answer is depth-buffer layering, not color override. Three z-layers:
PT_FABRIC offset -2 (front), Body/Sleeves/FABRIC_1 default, FABRIC_2
offset +1 (back). Where body covers, body wins (black). Where body has a
slit (zipper area), FABRIC_2's gray fills in unobstructed. Materials keep
CLO3D's original Kd values.

### `6572158` v44: stream retarget iterations as vertex animation

For LinkedIn flex content. Captures welded vertex state at frame 0
(pre-retarget penetration) and after each iteration. Un-welds each frame
to original-OBJ-vertex space, applies the same translate/scale undo as
the final mesh, packs as binary blob:
`[u32 LE num_frames][u32 LE verts_per_frame][float32 LE positions]`.
~26 frames × 26630 verts = ~8 MB raw, ~11 MB base64.

Frontend parses the OBJ for per-material vertex-index mappings, decodes
the frame blob, enables a Play Drape button. requestAnimationFrame loop
walks the frame index over 1.5 seconds, updates each mesh's position
attribute, recomputes normals.

### `4b2d5ec` v44.1: louder diagnostic when streaming data missing

Silent failure mode was hiding the most common cause of "Play Drape does
nothing": handler in production hadn't rebuilt yet. Add an explicit warn
log when iteration_frames_base64 is absent from the response.

### `1f0b2a5` v44.2: single flat OBJ-vertex mapping for animation

v44 looked up per-material mappings via `c.material.name`. Animation logs
fired but cloth never moved.

Cause: CLO3D's OBJ has 26 `usemtl` blocks but only 11 unique materials,
and no `o` lines. With no object delimiters, three.js OBJLoader puts
everything into ONE BufferGeometry on ONE Mesh, with the mesh's material
set to an ARRAY (per-face groups index into it). c.material.name is
undefined because Arrays have no .name.

Fix: replace per-material mapping with a single flat Uint32Array in OBJ
face-traversal order. Three.js OBJLoader's position attribute is laid out
in the same order, so the flat mapping indexes into it directly. No
material-name lookup. Diagnostic on frame 0 logs mesh count, attribute
lengths, applied count.

### `6db1702` v44.3: animation duration slider + loop + stop

The 1.5s default felt under 1s because frames 0-15 are mostly hidden
inside the body. Add a duration slider (1-8s, default 3s), Loop checkbox,
and Stop button. Stop snaps to the final settled pose so the garment
never lingers in an in-progress deformation.

For content recording: 4-6s with Loop on, capture 2-3 cycles, trim to
the cleanest one.

## Key structural breakthroughs of the day

**Stop running Newton.** v18-v35 was a week of fighting cloth_reference_drag's
miscategorized panel votes. The drag was the source of every artifact, not
the symptom. Disabling the sim and shipping the retarget directly was the
structural answer that the previous week of tweaking refused to find.

**The handler was shipping empty texture data.** Four versions of frontend
MTLLoader fixes were trying to render textures from a backend that wasn't
sending any. The mtllib-name mismatch silently skipped the whole packaging
block. Once v39 fixed it, frontend texture work could actually be evaluated.

**Decals are flat graphics, not lit cloth.** MeshBasicMaterial with
toneMapped=false renders texture pixel colors directly. ACES tone mapping
+ PBR is wrong for decals.

**Coplanar surfaces need polygonOffset.** When v26 retarget snaps every
vert to body+12mm, CLO3D's intentional layer offsets between print/body/
binding fabrics collapse to coplanar geometry. Industry-standard fix is
polygonOffset, not Kd hacks or material reordering.

**OBJLoader produces ONE mesh with material array** when the OBJ has no
`o` lines. c.material is Array, c.material.name is undefined. Animation
playback needs a single flat OBJ-traversal mapping, not a per-material map.

## Meta-lesson

Yesterday's lesson was "read the upstream source on day one." Today's:
**when you've been tweaking for more than two iterations, the layer you're
tweaking is the wrong layer.** v18-v35 was a week of moving panel-assignment
voting cells. v36 deleted the entire force that used those votes. v40-v42
was three frontend material tweaks for white backgrounds. v43 swapped Kd
hacks for depth layering.

Both were structural answers that took 30 minutes to write once we stopped
fighting symptom-level fixes. The "stop tweaking, go structural" feedback
memory is worth its weight in gold.

## Tomorrow's planning session (2026-05-04 evening)

Topic: how to wire today's drape into the actual product architecture.

The core idea: **drape is now a per-shopper background job at sign-up.**

  Shopper signs up.
  Avatar is generated (existing tryonline endpoint).
  For every garment in every connected brand catalog, queue a drape job
  against this shopper's body. Output GLB is written to a per-shopper
  Supabase Storage bucket keyed by (shopper_id, garment_id, size).
  When the shopper opens any product page, the iframe lookup is
  (shopper_id, garment_id, size) into Storage. Cache hit, zero latency
  fetch, render in well under one second. Fits perfectly because it
  was draped on this exact body shape.

Three open questions to settle tomorrow:

1. **Cost shape.** Per-shopper drape farm. ~50 SKUs (Ramin) × 4 sizes ×
   ~20s drape time = ~3300s = ~55 RunPod GPU minutes per shopper sign-up.
   At ~$0.50/hr that is ~$0.45 per shopper. At scale (10k shoppers, 50
   brands × 50 SKUs each) the math changes. Discuss whether per-shopper
   pre-compute is the right call vs body-shape clustering at the brand
   level (one drape per cluster, shoppers map to clusters).

2. **Sign-up to ready latency.** A shopper can't open the iframe at
   sign-up if drapes are still queued. Decide UX: "your closet is being
   prepared, ready in ~30 minutes" with email when done? Or render a
   placeholder until first drape lands?

3. **Backfill for existing shoppers.** The shoppers already in the
   system haven't been draped against any garment. Plan a backfill pass:
   for each existing shopper avatar, queue drape jobs against the active
   brand catalog. Decide priority (newest first? most active first?) and
   throttle (RunPod has concurrency limits).

Also worth touching:

- API surface: shopper-side `GET /api/drape/lookup?garment=...&size=...`
  returning a signed Supabase URL. Brand-side queue management endpoints.
- Schema: `draped_meshes` table already exists per CLAUDE.md. Verify its
  columns map to (shopper_id, garment_id, size) lookup pattern.
- Cache miss UX (new SKU just uploaded by brand, shopper hits PDP before
  drape finishes): graceful "preparing your fit" with email-when-ready.
- Triggering: brand connects Shopify → catalog ingest → drape queue
  per active shopper. Or only when first shopper hits a SKU.

The full architecture spec is already in
`docs/strategy/DRAPING_SHIPPABLE_REQUIREMENTS.md`. Tomorrow's session
should review it against today's working pipeline and translate the
"shopper signs up" flow above into a concrete build plan.
